# Доступ пользователей

Вход общий: индивидуальный логин и PIN из четырёх цифр. Существующий администратор сохраняет полный доступ. Новые реальные аккаунты автоматически не создаются.

## Переменные Production

- `DASHBOARD_USERS_JSON`: массив пользователей, тип Vercel **encrypted**, только Production. Начальное значение `[]`. PIN хранится как salted scrypt hash, исходный PIN не сохраняется. Тип Sensitive для этой переменной не подходит: серверу нужен доступ к актуальному реестру через API.
- `DASHBOARD_USERS_VERCEL_TOKEN`: отдельный серверный токен Vercel API, **Sensitive**, только Production. Нужны чтение и изменение переменных нужного проекта. Выберите минимально доступную область доступа и срок жизни. Не используйте `NEXT_PUBLIC_`, не передавайте токен в браузер, репозиторий или чат.
- `DASHBOARD_USERS_PROJECT_ID`, `DASHBOARD_USERS_TEAM_ID`, `DASHBOARD_USERS_ENV_ID`: идентификаторы существующего проекта, команды и production-переменной `DASHBOARD_USERS_JSON`. Последняя должна принадлежать только Production; общие с Preview переменные отклоняются.

`AUTH_SECRET`, `ADMIN_LOGIN`, `ADMIN_PASSWORD_HASH`, `DATABASE_URL` и `CONNECTIONS_ENCRYPTION_KEY` остаются прежними. Менять ключи или источники не требуется.

При первой установке выполнить `node scripts/migrate-user-access.cjs`: создаются только таблицы `mart_login_attempts` и `mart_user_write_lock`, без данных пользователей и без изменения таблиц источников. После добавления серверного токена нужен production redeploy, чтобы приложение получило новую переменную.

## Первый пользователь

1. Войти существующим администратором.
2. Открыть «Администрирование» → «Пользователи» → «Создать пользователя».
3. Указать согласованные с владельцем логин и четырёхзначный PIN; выбрать разрешённые разделы.
4. Сохранить. PIN не возвращается в ответе и никогда не подставляется в форму редактирования. Передать согласованные реквизиты пользователю отдельно.

Изменение логина, PIN, прав или переключателя «Доступ включён» отзывает прежние сессии пользователя. Пустой «Новый PIN» сохраняет прежний хеш. Для отключения снять «Доступ включён» и сохранить. Удаление аккаунтов не требуется для отзыва доступа.

При включённом Vercel API реестр читается без кеша при проверке сессии. Изменения пользователей применяются без нового deploy. При недоступности API пользовательский доступ закрывается, а вход администратора остаётся независимым от реестра. Старая копия из окружения не используется как запасной вариант.

Без токена Vercel API доступен статический реестр `DASHBOARD_USERS_JSON`, но управление через админ-панель выключено. Его ручные изменения вступают в силу только после redeploy. Для ручной подготовки хеша существует `node scripts/hash-password.mjs` со скрытым вводом; реальный PIN не помещать в аргументы команд. Без корректной конфигурации API панель не выдаёт сохранение за успешное.

Старые `USER_LOGIN` / `USER_PASSWORD_HASH` поддерживаются. Чтобы управлять таким пользователем из панели, создать запись с тем же логином и новым согласованным PIN. Эта запись имеет приоритет, в том числе при отключении. Пока задан `USER_LOGIN`, переименование этой записи запрещено, чтобы прежний доступ не восстановился.

## Права и защита

Пользователь видит только назначенные разделы и их показатели. Фильтры просмотра и сравнение периодов доступны, но они не сохраняют настройки по умолчанию. Администрирование, источники, пользователи, сохранение и принудительное обновление скрыты и защищены сервером. GET дашборда не запускает запись снимков или синхронизацию сохранённых подключений от имени пользователя. Ответ API содержит только данные разрешённых разделов.

Общий лимит PIN: не более пяти проверок в 15 минут, успешный вход сбрасывает счётчик. SQL хранит только HMAC идентификатора и счётчик. Без доступной таблицы защита закрывает вход, не пропуская запросы без лимита. Форма использует прежнюю HttpOnly Secure SameSite-сессию и проверку Origin.

Параллельные сохранения из панели сериализуются короткой SQL-блокировкой и проверкой версии. Ручное редактирование переменной в Vercel не следует выполнять одновременно с изменениями в панели.

## Проверки

`npm test` включает изолированные проверки входа/выхода обеих ролей, прямых URL, административных API, закрытых разделов в JSON, отключения и смены прав, отсутствия PIN/хешей в ответах, конфликта версий и недоступности реестра.

После `npm run build`: `AGENT_BROWSER_BIN=<путь к agent-browser> node tests/user-access-browser.cjs`. Тест использует временный локальный сервер и данные только в памяти процесса; он не создаёт production-аккаунты и не подключается к реальным источникам. Форма редактора проверяется с подменённым ответом API в браузере, серверное сохранение проверяется отдельно в модульных тестах с подменённым Vercel API.

Справка Vercel: [чтение защищённой переменной](https://vercel.com/docs/rest-api/projects/retrieve-the-decrypted-value-of-an-environment-variable-of-a-project-by-id), [изменение переменной](https://vercel.com/docs/rest-api/projects/edit-an-environment-variable).
