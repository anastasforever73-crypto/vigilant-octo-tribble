# Март-Трейд — защищённый дашборд

Next.js App Router. Локальная версия доработана по ТЗ; автоматическая публикация не выполняется. Актуальные итоги меню и настройки базы — в [MENU-STORAGE-REPORT.md](MENU-STORAGE-REPORT.md); устройство источников — в [ADMIN-SOURCES-REPORT.md](ADMIN-SOURCES-REPORT.md). Предыдущая проверка сохранена в [VERIFICATION.md](VERIFICATION.md).

## Запуск и учётные записи

1. Установить зависимости: `npm ci`.
2. Выполнить `npm run setup-auth` в интерактивном терминале. Скрипт запросит разные логины, два пароля с подтверждением и скрытым вводом, создаст 48 случайных байт для AUTH_SECRET и запишет хеши в `.env.local` с правами 600. Другие настройки источников сохраняются. Уже настроенная авторизация не перезаписывается. Скрипт не создаёт стандартных паролей.
3. Дополнить `.env.local` серверными реквизитами источников из `.env.example`. Пример содержит только имена переменных. После изменения настроек перезапустить локальный сервер.
4. `npm run dev` для разработки либо `npm run build` и `npm start` для локальной production-проверки.

Для постоянного просмотра в Codespaces на порту **3100**: `npm run build`, затем `npm run start:codespaces` в отдельном терминале. Эта команда явно задаёт `PORT=3100` и адрес привязки `0.0.0.0`, необходимый для автоматического обнаружения порта. Открывайте **Ports → 3100 → Open in Browser**. Браузерные тесты запускают временные серверы и останавливают их после проверки — такой сервер не заменяет постоянный запуск приложения. Порт оставляйте приватным.

В серверном выводе записи `AUTH_LOGIN` содержат только результат, статус, формат запроса либо роль после успешного входа. Логины, пароли, заголовки и cookie не журналируются.

Диагностика остановленного сервера и реального проброса 3100: [CODESPACES-3100-VERIFICATION.md](CODESPACES-3100-VERIFICATION.md).

Для сброса паролей обеих ролей выполните `npm run setup-auth -- --reset` в интерактивном терминале. Новые пароли должны содержать ровно 4 символа и вводятся скрыто с подтверждением. Существующие логины и настройки источников, включая многострочные значения, сохраняются. Хеши scrypt и `AUTH_SECRET` заменяются, прежние сессии становятся недействительными. Без `--reset` перезапись авторизации запрещена. Сброс не выполняется автоматически; после него перезапустите локальный сервер. Старые пароли другой длины больше не принимаются.

Скрипт `node scripts/hash-password.mjs` читает пароль из стандартного ввода и выводит только хеш. Формат: `scrypt$32768$8$3$<salt-hex>$<key-hex>`, соль 16 байт, ключ 64 байта. Допустим пароль длиной ровно 4 символа Unicode; более короткие и более длинные пароли отклоняются в форме, API и скриптах. Не передавайте его аргументом команды и не записывайте в историю shell.

Для скрытого ввода в Bash:

```bash
read -r -s -p 'Пароль: ' MART_PASSWORD
printf '%s' "$MART_PASSWORD" | node scripts/hash-password.mjs
unset MART_PASSWORD
```

Скрипт экранирует каждый `$` в хеше как `\$`: загрузчик Next.js раскрывает переменные даже внутри одинарных кавычек. При ручной записи требуется такое же экранирование. В Vercel вносите исходный хеш с обычными `$`, без экранирования и окружающих кавычек. Не используйте переменные с префиксом `NEXT_PUBLIC_` для реквизитов.

Сессия действует восемь часов, подписана HMAC-SHA256, cookie имеет `HttpOnly`, `SameSite=Strict`, `Secure` во всех режимах. Сервер проверяет срок, подпись, роль и версию учётных данных. Изменение хеша/логина отзывает сессии соответствующей роли; смена `AUTH_SECRET` отзывает все сессии. Выход удаляет cookie браузера. Индивидуальный серверный отзыв украденной cookie до её истечения требует постоянного хранилища сессий.

Форма входа отправляет реквизиты только в теле POST: JSON при работающем JavaScript и обычную HTML-форму при отключённых скриптах. После обычной формы сервер перенаправляет на дашборд либо `/login?error=auth`; реквизиты в URL не включаются. Для страницы входа и маршрутов авторизации заданы `Referrer-Policy: strict-origin` и запрет кеширования.

В GitHub Codespaces допустимый внешний адрес определяется серверными `CODESPACES=true`, `CODESPACE_NAME`, `GITHUB_CODESPACES_PORT_FORWARDING_DOMAIN` и `PORT` (по умолчанию 3000). Заголовки `X-Forwarded-*` не расширяют список доверенных адресов. Проверка применяется к входу и остальным изменяющим запросам; посторонние адреса и отсутствующий `Origin` отклоняются. При запуске на другом порту задайте соответствующий `PORT`.

Прокси Codespaces может переписать `Host` и `Origin` на `localhost:<порт>`. Для такого запроса внешний адрес восстанавливается только при локальном целевом хосте, совпадающем порте и точном `X-Forwarded-Host`, вычисленном из серверного окружения. Благодаря этому HTML-форма также перенаправляет обратно на HTTPS-адрес Codespaces. Адрес привязки Next.js `0.0.0.0` поддерживается без разрешения произвольных хостов.

## Действующие подключения

Все реквизиты читаются только из переменных окружения. Нет сохранения в localStorage, cookie или памяти процесса. На странице источников администратор может проверить новые реквизиты без сохранения, получить список листов и проверить существующее сопоставление диапазонов. API не возвращает введённые реквизиты, email сервисного аккаунта, токены и ключи.

Google Sheets: `GOOGLE_SHEET_ID`, `GOOGLE_SERVICE_ACCOUNT_EMAIL`, `GOOGLE_PRIVATE_KEY`. Разрешены ID и ссылки `https://docs.google.com/spreadsheets/d/...`. Включите Google Sheets API и предоставьте сервисному аккаунту роль «Читатель» на конкретной таблице.

Таблица дебиторки: `DEBT_GOOGLE_SHEET_ID` и те же серверные реквизиты Google. Названия исходных листов задаются `DEBT_TRANSIT_SHEET` (по умолчанию «Транзит») и `DEBT_STOCK_SHEET` (по умолчанию «Склад»). Для таблицы «Плита» используются «Заказы» и «Склад». В первом источнике нужны «Дата УПД», «Ст-ть заказа», «Остаток долга», «Конечный получатель»; во втором — «Дата отгрузки», «сумма», «Долг», «Направление». История читается из «Архив ДЗ», текущая ДЗ не берётся из готового «Лист6». Расчёт следует `scripts/Otchet_DZ.gs`: пустые/нечисловые остатки дают 0, исключённые строки показываются с причинами, недоступный лист даёт явно частичный результат. Формула, реальные суммы и ограничения описаны в [RECEIVABLES-PARITY.md](RECEIVABLES-PARITY.md).

Финтабло: `FINTABLO_API_BASE_URL` (совместимость: `FINTABLO_API_URL`) и `FINTABLO_API_TOKEN`. Сохранён существующий адаптер API `https://api.fintablo.ru`; произвольные хосты, авторизация в URL и перенаправления запрещены. Используются существующие маршруты `/v1/moneybag`, `/v1/transaction`, `/v1/pnl-category`, `/v1/category`, `/v1/partner`, `/v1/pnl-item`. Реальная работоспособность должна быть подтверждена токеном владельца и доступом к его данным.

`GOOGLE_SHEETS_ENABLED=false`, `FINTABLO_ENABLED=false`, `DEBT_ENABLED=false` отключают чтение соответствующего источника без удаления файлов. Отсутствие этих флагов означает, что источник разрешён, но для подключения всё равно требуются реквизиты.

### Существующее сопоставление Google Sheets

| Переменная | Лист по умолчанию | Диапазон |
| --- | --- | --- |
| `CASH_SHEET` | ДДС недельный - по статьям | A2:N |
| `ORDERS_SHEET` | техн.лист плита - заказы | A2:X |
| `DEBTOR_SHEET` | дебиторка (расчет) | A1:C30 |
| `FACTORY_SHEET` | Кредиторка по Заводу (1с) | A4:O |
| `WALLET_SHEET` | Техн.лист (кошелек) | A2:J |
| `ACCOUNT_SHEET` | техн рс остатки | A2:B |

Позиции колонок сохранены в `app/lib/google-dashboard.ts`. Существующий формат ДДС: дата E, сумма F, источник G, контрагент I, статья K, поток L. Заказы: дата A, номер B, плательщик C, клиент D, регион E, товар G, количество H, вид оплаты J, выручка L, менеджер R, направление S, объём U, оплачено V, долг W, доставка O. Выбор другого листа сам по себе не доказывает такое же назначение колонок — владелец обязан подтвердить схему. `GOOGLE_SHEET_RANGES` задаёт JSON-массив диапазонов только для совместимого `/api/google-sheets` и не меняет расчётный адаптер дашборда.

Полученные операции фильтруются по выбранному и предыдущему периоду. ДДС берётся целиком из Финтабло при его доступности, иначе из Google Sheets: операции двух источников не складываются. Заказы и агрегаты задолженности берутся из Google Sheets. Остатки Финтабло относятся к фактической дате получения, не выдаются за исторические. Сравнение остатков и задолженности без истории не рассчитывается.

Локальные `mart-data.json` и `app/mart-data.json` сохранены без изменений, но не импортируются в клиентский пакет и не подставляются при ошибке подключения. Исходный компонент сохранён в `archive/dashboard-before-auth.tsx.txt`, включая ранее неиспользуемые макеты; этот архив не участвует в сборке. Товар, логистика и ОПиУ до доработки уже показывали отсутствие подтверждённых данных. Для заполнения нужны реальные источники и согласованное сопоставление, демонстрационные таблицы из неиспользуемых макетов не включены.

## Административная панель и постоянное хранилище

Раздел «Источники данных» содержит редактор подключений для admin. Роль user видит только «Статус источников». Все операции управления защищены серверным `guard(request, 'admin')`; скрытие кнопок не является единственной защитой.

Для сохранения подготовлен Neon PostgreSQL с драйвером `@neondatabase/serverless`. Нужны серверные `DATABASE_URL` и `CONNECTIONS_ENCRYPTION_KEY` (32 случайных байта, 64 hex-символа, отдельный ключ — не `AUTH_SECRET`). В приватной базе нужно явно выполнить [migrations/001-connections.sql](migrations/001-connections.sql). Миграция и подключение сервиса автоматически не запускаются. До готовности базы сохранение возвращает 503, фиктивных записей нет.

- `mart_connections`: публичная конфигурация, версия, включение, зашифрованные секреты, статус и последний успех.
- `mart_source_links`: выбранные разделы и подтверждённое сопоставление. Уникальная пара `(section, dataset)` запрещает двойное назначение одного показателя.
- `mart_source_snapshots`: зашифрованные нормализованные данные по периоду и версии подключения.
- `mart_source_runs`: результаты ручных синхронизаций с безопасными сообщениями.

Секреты и снимки шифруются AES-256-GCM на сервере, ключ хранится отдельно от БД. API никогда не возвращает сохранённые секреты. Пустое секретное поле при редактировании сохраняет прежнее значение. Смена ключа шифрования требует перешифрования существующих записей.

Новое подключение можно связать с несколькими разделами. Для одного набора сохраняются одинаковые лист и колонки. Конфликт с другим источником отклоняется; администратор может явно выбрать текущее подключение приоритетным. При изменении конфигурации требуется новая синхронизация; выключенный источник не подменяется другим молча. Отключение сохраняет историю, удаление удаляет запись, связи и снимки после подтверждения в интерфейсе.

Google Sheets показывает реальные листы и заголовки выбранной строки. Автоматического назначения колонок нет; при чтении проверяются подтверждённые заголовки. Финтабло использует существующие методы `/v1/moneybag`, `/v1/transaction` и `/v1/pnl-item` с прежними справочниками; выбор организаций отдельно не реализован. ОПиУ показывает подтверждённые записи, не рассчитывая прибыль из ДДС. CRM имеет расширяемый интерфейс, но до получения документации конкретной системы не выполняет произвольные HTTP-запросы. Для товара и логистики ещё нужны подтверждённые схемы данных.

Существующие подключения из окружения остаются в прежнем режиме чтения. Для управления ими через панель создайте сохранённое подключение и явно назначьте его разделам; автоматического переноса секретов и сопоставлений нет. Совместимый `/api/settings` остаётся старым интерфейсом чтения настроек, а управление новыми подключениями использует `/api/connections`.

### Ввод реквизитов через панель

1. После настройки серверного хранилища войдите как admin и откройте «Источники данных».
2. Создайте Google Sheets: название, ссылка на таблицу, email и private key сервисного аккаунта. Сначала сохраните без связей — редактор останется открытым, секреты будут храниться на сервере.
3. Нажмите «Проверить подключение», добавьте связь, выберите лист и строку заголовков. Получите заголовки, сопоставьте обязательные поля и подтвердите целевую вкладку. Сохраните и нажмите «Обновить данные» за выбранный период.
4. Для Финтабло создайте отдельное подключение с токеном. Официальный API используется по умолчанию. После проверки выберите счета и наборы ДДС/остатков. Для ОПиУ используйте подключение без фильтра счетов.
5. CRM сохраняется как подготовка: название, документация, URL, способ авторизации. Новая связь направляется в «Продажи по менеджерам». Получение полей, воронок и менеджеров требует адаптера конкретной CRM; до этого синхронизация не работает.

После проверки несохранённого подключения секретные поля очищаются; перед сохранением реквизиты нужно ввести снова. Сервер отклоняет Google Sheets и Финтабло без необходимых реквизитов. После сохранения пустые поля сохраняют прежние секреты.

Полный отчёт и ручная проверка: [ADMIN-SOURCES-REPORT.md](ADMIN-SOURCES-REPORT.md).

Перед публикацией также требуется общий лимит попыток входа на уровне Vercel Firewall либо постоянного серверного хранилища. Реализована блокировка на 15 минут после 5 неудачных попыток на роль/неизвестные логины. Успешный вход обнуляет счётчик; во время блокировки даже правильный пароль не принимается. Параллельные проверки одной роли выполняются последовательно. Счётчик хранится в памяти одного процесса и теряется при его перезапуске; это не общий лимит для нескольких экземпляров сервера. При отсутствии обязательных параметров авторизации сайт закрыт для входа.

## Проверки

- `npm test` — серверные модульные проверки с изолированными тестовыми данными.
- `python3 tests/setup-auth-test.py` — интерактивная настройка и сброс через npm во временных Git-проектах.
- `npm run lint`.
- `npx tsc --noEmit --incremental false`.
- `npm run build`.
- `MART_TEST_PRODUCTION=1 AGENT_BROWSER_BIN=/path/to/agent-browser node tests/auth-browser-check.mjs` — после сборки запускает отдельный локальный сервер на 3100 с временными учётными данными. Проверяет вход, роли, меню, вкладки и интерфейсы источников. Не меняет `.env.local`, не создаёт подключения и не обращается к опубликованному сайту. `tests/browser-check.mjs` запускает тот же сценарий.
- `MART_TEST_AUTH_ONLY=1 AGENT_BROWSER_BIN=/path/to/agent-browser node tests/auth-browser-check.mjs` — отдельная проверка входа user/admin, ошибок, ролей и выхода с включённым и отключённым JavaScript. Отчёт сохраняется в `artifacts/verification/auth-focused-report.json`. Можно добавить `MART_TEST_PRODUCTION=1` для проверки собранной версии.

Общие принципы серверных проверок сверены с [руководством Next.js](https://nextjs.org/docs/app/guides/authentication), криптографические функции — с [документацией Node.js](https://nodejs.org/api/crypto.html).

Скрипт первоначальной настройки проверяет `.gitignore`, индекс и доступную историю Git. Если `.env.local` уже отслеживается или встречается в истории, запись запрещена. Эти проверки защищают обычный процесс Git; намеренный `git add -f`, изменение правил или ручная загрузка файла обходят `.gitignore`. Скрипт не публикует файлы и не меняет Vercel.


### Планирование поступлений и списаний

Раздел «Планирование» показывает план поступлений, план списаний и плановый денежный поток (поступления минус списания) за период, выбранный в общем календаре. Для каждого направления доступны категории с суммами и долями, детализация операций и сравнение с предыдущим периодом такой же длительности. Отсутствие источника отображается как «Нет данных»; подключённый пустой план — как нулевой итог.

В «Источники и архив» откройте подключение Google Sheets и добавьте две связи с целевой вкладкой «Планирование»: наборы «План поступлений» и «План списаний». Они могут использовать разные листы или разные колонки одного листа. Назначьте обязательные поля «Плановая дата», «Категория», «Плановая сумма», подтвердите сопоставление, сохраните подключение и обновите данные. Дата — день ожидаемой операции (для месячного плана можно использовать первое число месяца); сумма — положительная или нулевая, направление задаётся набором. Контрагент и комментарий необязательны. Отрицательные суммы и строки без обязательных значений отклоняются.

Для пользователей предоставьте отдельный доступ «Планирование» в разделе «Пользователи». Проверки расчётов, связей и границ доступа: `node tests/planning.test.cjs` (также входит в `npm test`).


### Оперативный остаток, НЛПК и Excel

Оперативный остаток рассчитывается по согласованной формуле: текущий общий остаток денежных средств + план поступлений − план списаний за выбранный период. Расчёт использует целые копейки. Если отсутствует текущий остаток или любой из планов, результат — «Нет данных»; подтверждённые нулевые планы учитываются как нули. Кредиторская задолженность НЛПК не вычитается повторно: плановые оплаты поставщику включаются в план списаний. При изменении периода пересчитываются оба плана и прогноз; агрегаты другого периода не переиспользуются.

В «Источники и архив» доступен набор Google Sheets «Кредиторская задолженность НЛПК» с целевой вкладкой «Оперативный дашборд» или «Расчёты и обязательства». Обязательные поля — дата остатка и остаток долга; документ, срок оплаты и комментарий необязательны. Назначенный лист должен содержать только остатки НЛПК, без повторной строки общего итога. На каждой дате должен быть полный снимок: детали документов на последнюю дату не позже окончания периода складываются, снимки разных дат не суммируются. Для одного сводного остатка достаточно одной строки на дату. Объединение снимков нескольких источников отключено; можно выбрать основной и резервный источник. Остаток отображается в оперативных показателях и в таблице документов задолженности.

Кнопка Excel находится в верхней панели. Раздел «Планирование» выгружает итоги, категории, сравнение периодов и операции; оперативный отчёт — планы и оперативный остаток; отчёт задолженности — снимок и документы НЛПК; ДДС — факт и выполнение плана. Выгрузка использует те же серверные показатели, период и права доступа, что и интерфейс.

Оформление новых карточек, планов и НЛПК следует локальным изображениям референса в `artifacts/reference`: зелёная верхняя панель, компактная навигация, карточки с суммой над названием, полосы выполнения плана и две колонки таблиц/графиков. Визуальная проверка с синтетическими данными: `AGENT_BROWSER_BIN=/path/to/agent-browser node tests/planning-reference-browser.mjs`; снимки находятся в `artifacts/reference-update`. Рабочие источники и учётные данные этот сценарий не меняет.

### Процент кошелька

Администратор вводит процент на «Оперативном дашборде» → «Кошелёк → безнал» → «Ставка приведения кошелька к безналу»: «Ставка надбавки, %» и «Действует с», затем нажимает «Сохранить процент». Ставка хранится в PostgreSQL (`migrations/007-wallet-percentage.sql`), допускает 0–100% и два знака после запятой. Для одной даты сохранение обновляет ставку; для новой даты добавляет запись. 0% отменяет надбавку начиная с этой даты.

Кошелёк с надбавкой = исходный остаток × (1 + процент / 100), округление до копеек. Общий остаток увеличивается на сумму надбавки к кошельку; операционный (плановый) остаток считается из нового общего остатка плюс план поступлений минус план списаний. Применяется последняя ставка, действующая на дату остатка; текущие счета используют дату снимка по Москве, исторические — дату остатка. Исходные архивные значения сохраняются без изменения, ставка применяется при чтении, включая Excel. После сохранения клиент сбрасывает кэш и запрашивает пересчёт без повторного импорта источников.

На оперативном дашборде кошелёк показан исходной суммой и безналичным эквивалентом со ставкой и датой действия. Рядом с общим остатком отдельной карточкой показан операционный остаток (общий остаток + план поступлений − план списаний). Если один из планов недоступен, карточка показывает отсутствие данных и причину. Настройка ставки также доступна администратору в «Источниках и архиве».

Остатки на оперативном дашборде зависят от конечной даты периода. Текущий снимок FinTablo используется только для той даты, к которой относится; для истории нужен датированный источник остатков. Если исторического снимка нет, возвращается отсутствие данных. Ставка кошелька выбирается на дату выбранного остатка. Изменение начала периода при той же конечной дате не меняет исходный остаток, но меняет операции и планы.

Для FinTablo остаток на выбранную дату рассчитывается из `surplus`/`surplusTimestamp` и фактических операций `isPlan=0` между фиксацией и выбранной датой. На счетах без фиксации применяется обратный расчёт от текущего остатка по фактическим движениям. Переводы учитываются на обоих счетах, повторные и родительские разбитые операции не дублируются. Когда отдельные связи планирования не назначены, планы читаются из плановых операций `isPlan=1` подтверждённого источника ДДС FinTablo за выбранный период; назначенные вручную источники планов всегда имеют приоритет.
