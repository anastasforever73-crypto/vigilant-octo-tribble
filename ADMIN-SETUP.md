# Однократная подготовка и дальнейшая работа через админку

## Три первоначальных действия

1. Подключить Neon к существующему проекту `mart-treid` и задать серверный `DATABASE_URL` в Vercel и локальном `.env.local`. Подробные нажатия: [VERCEL-STORAGE-SETUP.md](VERCEL-STORAGE-SETUP.md).
2. Задать отдельный серверный `CONNECTIONS_ENCRYPTION_KEY` в Vercel и локальном окружении. Локальный ключ уже создан. Для одной базы нужен один и тот же ключ; существующий рабочий ключ не заменять без переноса зашифрованных данных. Значения не передавать в чат.
3. Из `/workspaces/vigilant-octo-tribble` применить миграцию одной командой:

   ```bash
   npm run storage:migrate
   ```

   Команда читает `.env.local` и применяет `migrations/001-connections.sql` одной транзакцией. Затем перезапустить локальный сервер. Публикация не требуется.

Это инфраструктурные действия, они не повторяются для каждого источника.

## После подготовки — только через дашборд

Войти как admin → «Источники данных» → «Проверить готовность системы». Три проверки должны показывать «Готово»: база, миграция, серверный ключ. Проверка также доступна admin по `GET /api/connections/readiness`, без секретов в ответе.

Если хранилище не готово, показывается «Требуется первоначальная настройка хранилища», подробная причина и результаты трёх проверок. Формы источников и неработающие кнопки добавления не показываются. Повторная проверка открывает управление после настройки хранилища.

### Google Sheets и таблица задолженности

1. «Добавить подключение» → выбрать Google Sheets или Google Sheets — задолженность.
2. Ввести название, ссылку на таблицу, email и private key сервисного аккаунта. Сервисному аккаунту нужен доступ к этой таблице в Google; эти реквизиты в Vercel добавлять не нужно.
3. Сохранить без связей. Затем проверить подключение, выбрать реальные листы и строку заголовков, получить заголовки.
4. Назначить колонки полям, выбрать целевые вкладки, подтвердить и сохранить связи.
5. «Обновить данные» — загрузить выбранный период. Статус и дата последнего успешного обновления показываются в карточке.

### Финтабло

Добавить подключение, ввести название и API-токен, сохранить. Проверить доступ, выбрать реальные счета и наборы ДДС/остатков/ОПиУ, подтвердить вкладки и сохранить. Запустить обновление. Для ОПиУ используется отдельное подключение без фильтра счетов.

### CRM

По решению пользователя API-интеграция пока пропущена: название и документация API конкретной системы отсутствуют. Через панель можно сохранить конфигурацию CRM и реквизиты для будущего адаптера. Проверка и синхронизация честно сообщают о необходимости адаптера; воронки, менеджеры и сделки не имитируются.

### Повседневное управление

Редактирование, замена реквизитов, включение, отключение, удаление с подтверждением, ручное обновление, просмотр статусов и даты успешной синхронизации выполняются в панели. Для нового источника не нужны новые переменные Vercel и новая миграция.

## Защита реквизитов

- Создание и редактирование реквизитов: только POST, JSON в теле запроса. Проверки подключения и синхронизация также POST.
- Совместимый PATCH поддерживает только переключение состояния и не принимает секретные поля.
- Секреты шифруются AES-256-GCM на сервере; ключ шифрования хранится отдельно от PostgreSQL.
- Ответы содержат только наличие реквизитов и фиксированную маску `••••••••`, без реальных символов и без раскрытия длины. Форма редактирования не подставляет маску в значение поля.
- Пустое поле оставляет прежний секрет. Новый ввод заменяет его. Маска как новое секретное значение отклоняется сервером.
- Поля очищаются после проверки и сохранения. Реквизиты вводятся в браузер пользователем и уходят в теле POST; сохранённые реквизиты не возвращаются из базы в браузер.
- Все административные API проверяют роль; изменяющие запросы — также Origin. Ответы запрещают кэширование.

## Граница текущей проверки

В локальном окружении отсутствует `DATABASE_URL`; ключ задан. Поэтому полный успешный сценарий «форма → сервер → PostgreSQL → реальный Google/Финтабло → синхронизация» пока выполнить нельзя. Проверки недоступного хранилища и защиты API не подменяют проверку реального сохранения.

После добавления `DATABASE_URL` можно применить миграцию указанной командой и выполнить `npm run storage:verify` для серверного пути CRUD. Затем остаётся браузерная проверка реального источника с реквизитами, введёнными владельцем через панель. Проект не опубликован.
