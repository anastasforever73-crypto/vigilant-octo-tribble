# PostgreSQL Timeweb и приложение в России

## Выбранное размещение

Проверено в панели 10 ноября 2026: приложение Mart Treid `286423` уже работает в **Москва, MSK-1 (Россия)**, 1 CPU / 2 ГБ RAM / 30 ГБ, без приватной сети. Менять регион приложения не требуется. В форме создания БД доступна **PostgreSQL 18, Москва MSK-1**. Санкт-Петербург в момент проверки распродан; зарубежные регионы не выбираем.

Рекомендуемый начальный кластер: Premium NVMe, **1 CPU / 2 ГБ RAM / 20 ГБ**, один мастер без реплик. Это начальная оценка по текущей копии размером около 134 МБ, а не нагрузочное тестирование будущего production. Драйвер использует два профиля таймаутов (8 и 15 секунд), каждый со своим пулом до пяти соединений: суммарно до 10 на процесс приложения. Рекомендуемый запас — минимум 40 разрешённых соединений для перекрытия старого/нового контейнеров при деплое, миграций и администратора; при нескольких процессах/стендах суммируйте лимиты. Специальных расширений не требуется. Код использует UUID, JSONB, identity, PostgreSQL-транзакции и `pg_stat_ssl`. Код проверен на PostgreSQL **18.6**.

В просмотренной форме тариф 2 000 ₽/мес, ежедневный бэкап 120 ₽/мес и дополнительная опция «Отмена удаления» 200 ₽/мес: **2 320 ₽/мес** при этих выбранных опциях. Без «Отмены удаления» — 2 120 ₽/мес. Это цена базы и перечисленных опций из формы на момент проверки, без стоимости уже существующего приложения и возможной отдельной тарификации IP. Перед заказом проверьте итог в панели. Минимальный тариф 1 ГБ имеет ограничения по пользователям/управлению параметрами, поэтому выбран 2 ГБ.

## Создание базы в панели

1. Откройте Timeweb Cloud → **Базы данных → Создать**. Выберите PostgreSQL **18**, регион **Москва — MSK-1**, Premium NVMe **1 CPU / 2 ГБ / 20 ГБ**, **без реплик**. Версию после создания изменить нельзя; проверьте выбор перед заказом.
2. Назовите кластер `mart-trade-pg-ru`. Укажите тот же проект «Общий проект» (`3163091`), что у приложения. Включите ежедневные резервные копии. «Отмена удаления» — дополнительная платная опция; цену и необходимость подтвердите при заказе. Для диска задайте уведомление о заполнении; автомасштабирование включает дополнительные расходы, поэтому не включайте его без выбранного бюджета.
3. В разделе **Сети → Приватные сети** создайте BGP-сеть `mart-trade-msk1` в **MSK-1**. Выберите её в форме БД. Не используйте другую зону или другой VPC только с похожим названием. Для CIDR можно использовать незанятую подсеть RFC1918, например `10.73.0.0/24`, если панель разрешает такой диапазон; адреса назначает панель.
4. Задайте новый пароль пользователя БД самостоятельно и сохраните его в менеджере паролей/локальном защищённом файле. Не используйте AUTH_SECRET или ключ шифрования как пароль БД. Пароль, URI и PEM-ключ Google нельзя отправлять в чат или Git. Нажмите **Заказать** только после проверки тарифа и опций. Дождитесь статуса готовности.
5. Внутри нового кластера создайте **отдельную пустую базу** `mart_trade` с кодировкой UTF8. Если панель создала базу автоматически, убедитесь, что схема public не содержит пользовательских таблиц. Нужна именно новая база; действующая Vercel/Neon не используется и не очищается.
6. Во вкладке **Подключение** включите/проверьте TLS, скачайте корневой CA и сохраните DNS-имя из TLS-реквизитов. Timeweb документирует TLS через домен и необходимость публичного подключения при его включении. Наличие TLS на приватном endpoint надо проверить отдельно: не считайте приватный IP доказательством TLS и не отключайте проверку сертификата для обхода ошибки.
7. Приложение 286423 → **Сеть → Подключить**: панель сейчас предлагает первое подключение приватной сети. Выберите тот же VPC `mart-trade-msk1`. Это сетевое изменение может вызвать краткий перерыв. Не меняйте регион/тариф приложения: в его текущей локации форма изменения конфигурации сейчас показывает отсутствие свободных ресурсов. Если подключение текущего приложения к выбранной сети не поддерживается, оставьте его работающим и согласуйте перенос сети/клонирование отдельно.
8. Предпочтительный путь — приватный IP базы + TLS с проверкой DNS-имени сертификата. Если managed endpoint не принимает TLS на приватном IP, используйте **DNS TLS endpoint в той же MSK-1**, ограничив внешние подключения firewall/allowlist реальным исходящим IP приложения и временным IP администратора. Не предполагайте, что входящий публичный IP приложения обязательно совпадает с исходящим — проверьте egress в панели/консоли. Если firewall для этого endpoint недоступен, этот запасной вариант нельзя считать готовым. Не открывайте PostgreSQL всему интернету и не используйте `rejectUnauthorized:false`.
9. Сохраните реквизиты новой базы и CA в защищённый локальный JSON вне Git. Сообщите только путь к файлу, не его содержимое. Для миграции по приватному IP запускайте команды с доверенного хоста/консоли приложения в том же VPC: локальный ноутбук без VPN туда не подключится. Публичный временный доступ администратора после миграции закрывается.

## Роли и доступ к схеме

Для восстановления используйте владельца новой пустой базы / отдельную migration-роль с CREATE в public. После переноса желательно выдать приложению отдельную runtime-роль без SUPERUSER и без прав создания/удаления схемы. Ей нужны CONNECT к базе, USAGE к public, SELECT/INSERT/UPDATE/DELETE на всех десяти таблицах, USAGE/SELECT на identity-sequences. Миграции выполняет владелец, а не runtime-роль. Не используйте минимальный тариф, если он не позволяет создать нужные роли. Если панель ограничивает GRANT, проверьте права её штатного пользователя и зафиксируйте фактический набор до публикации.

При выполнении SQL от имени владельца новых объектов (имя runtime-роли подставляется оператором локально) выдайте также default privileges для будущих таблиц/sequences. Эти команды нельзя выполнять на исходной базе Neon. Пароль роли задаётся в панели, а не в Git-файле с SQL.

## Конфигурация нового драйвера

Существующие пять переменных Timeweb сохраняются **точно**:
`AUTH_SECRET`, `ADMIN_LOGIN`, `ADMIN_PASSWORD_HASH`, `USER_LOGIN`, `USER_PASSWORD_HASH`.
Для нового хранилища уже подготовлен отдельный локальный ключ шифрования; старый ключ и старая база не изменяются.

Дополнительные переменные:

| Переменная | Назначение |
|---|---|
| DATABASE_URL | URI только новой базы Timeweb, со всеми компонентами URL-encoded; значение не публикуется |
| DATABASE_SSL_MODE | `verify-full`; `require` также принудительно проверяет CA и имя. Отключение TLS разрешено кодом только для loopback-тестов |
| DATABASE_SSL_CA | PEM корневого сертификата из панели Timeweb; удобно для App Platform |
| DATABASE_SSL_CA_FILE | Альтернатива: абсолютный путь к CA, доступный внутри контейнера. Не задавать одновременно с DATABASE_SSL_CA |
| DATABASE_HOSTADDR | Необязательно: приватный IP для транспорта, если URI содержит TLS DNS-имя |
| DATABASE_TLS_SERVERNAME | DNS-имя из сертификата для проверки при подключении к IP |
| DATABASE_POOL_MAX | `5` на пул/профиль таймаута (до 10 на процесс приложения); не более 20 на пул по проверке конфигурации |
| CONNECTIONS_ENCRYPTION_KEY | Новый ключ **отдельного** хранилища; не применять к прежней Neon |
| APP_ORIGIN | `https://anastasforever73-crypto-vigilant-octo-tribble-e9e5.twc1.net` |

Драйвер не передаёт URI-параметры sslmode внутрь `pg`, где они могли бы заменить объект CA. TLS-конфигурация задаётся явно с `rejectUnauthorized:true`. Сертификат и имя сервера проверяются даже в приватной сети. Пул лениво создаётся в runtime; при production-сборке база не требуется. Для локальных CLI JSON предпочтительнее dotenv: символ `$` в хешах паролей не должен интерполироваться.

Восстановление проверяет отдельный endpoint/базу, но главная защита от ошибочного назначения — отказ при любой существующей таблице public внутри одной Serializable-транзакции. Не меняйте этот запрет и не очищайте базу ради его обхода.

## Перенос и проверка после создания

На доверенной машине с доступом к новой базе и проверенным checkout выполните `npm ci`. Секреты берутся из приватного JSON через MIGRATION_ENV_FILE; ни URI, ни пароль не передаются в командной строке.

```sh
# Только проверка подключения/SSL. Пароли и адреса не выводятся.
MIGRATION_ENV_FILE=/private/path/timeweb-target.json npm run storage:tls-check

# Offline-проверка плана и конфликтов логинов.
npm run recovery:plan -- /private/path/timeweb-target.json private-data/vercel-recovery-20261110.json

# После проверки назначения в том же JSON установить
# RECOVERY_CONFIRM_EMPTY_TARGET="new-isolated-timeweb-storage".
# Эта команда сама применяет все восемь миграций к ПУСТОЙ базе;
# не запускайте storage:migrate перед ней, иначе guard правильно откажет.
npm run recovery:import -- /private/path/timeweb-target.json private-data/vercel-recovery-20261110.json

MIGRATION_ENV_FILE=/private/path/timeweb-target.json npm run migration:check
MIGRATION_ENV_FILE=/private/path/timeweb-target.json npm run storage:check
```

Импорт переносит четыре подключения выключенными, пять точных определений привязок, двух управляемых пользователей с прежними хешами/правами/revision, две записи истории процентов и активные ограничения входа. Новый ключ шифрует пустые реквизиты; затем реквизиты вводятся заново в панели источников. Старые зашифрованные реквизиты, 101 снимок, 27 отчётов, 68 архивов входных данных и 479 записей прежнего журнала остаются в защищённой резервной копии; не выдаются за читаемые данные новой базы. Подробности ограничений и возможной read-only выгрузки через действующий Vercel — в `TIMEWEB-RECOVERY.md`.

Google JSON уже проверен: доступ к двум прежним таблицам есть. Финтабло требует действующего токена. CRM ранее выключена — оставляется выключенной. До проверки этих источников реальная полнота отчётов не подтверждена.

Сначала проверить новое окружение приложения с этой базой: вход, сохранение сессии, роли, источники, все разделы, архивы, Excel и сравнение доступных периодов с Vercel. Не применять `storage:verify` к исходной базе: он намеренно создаёт/изменяет/удаляет тестовую запись и предназначен только для новой тестовой базы.

## Выпуск и откат

После проверки новой базы загрузить её параметры и CA в Timeweb, сохранив пять старых настроек входа. Для приложения выбрать поддерживаемый Node.js 22, `npm run build`, `npm start`; маршрут `/build-info.json` служит проверкой версии. Сохранить защищённый экспорт настроек, предыдущий успешный деплой и backup новой базы.

Обновить **подключённую** `restore/timeweb-demo-clean` fast-forward push проверенного коммита; дождаться успешного деплоя, сравнить SHA панели и fingerprint `/build-info.json`. Проверить опубликованный вход и данные. До этого кандидат остаётся в `restore/timeweb-vercel-production`.

Откат к предыдущему успешному деплою Timeweb на `cc902f8111685d4ac9c56ca4ebd45452c504447f` и прежнему защищённому экспорту настроек. Ветка `rollback/timeweb-before-vercel-20261110` и git bundle сохранены. Ни старая Neon, ни новая Timeweb-база при откате не удаляются.
